Customer Resolution Agent
Deterministic Safety for Tier-1 Support

A customer support resolution agent engineered for Challenge 07. It safely automates tier-1 e-commerce order inquiries, enforces strict safety boundaries, escalates sensitive cases to human review, and validates all mock mutations with read-after-write verification.

Challenge 07 Objective & Intended User

Designed for Customer Support & Operations teams who need safe, bounded automation for repetitive e-commerce inquiries without risking unauthorized customer record mutations or hallucinations.

🛡️ Zero Hallucinated Actions

The agent operates under an absolute allowlist of permitted actions. It can only propose self-service resolution for verified safe cases or escalate to human specialists.

🔒 Read-After-Write Verification

Every proposed mock ticket update is executed in a simulated store and immediately verified by reading back the actual state. Any mismatch triggers an automatic fail-closed recovery.

👥 Deterministic Escalation

Delivery disputes, conflicting records, damaged merchandise, and fraud indicators are deterministically routed to human review queues. Model output cannot downgrade review triggers.

The "ACT, REPEAT, VERIFY, RECOVER" Workflow

A four-stage operational loop ensuring reliability, safety, and auditability across all synthetic resolutions.

STAGE 1

ACT

The agent inspects customer input and policy rules, selecting an action (self-service, ask customer, or human review) strictly within allowlisted boundaries.

STAGE 2

REPEAT

Mutations are executed against isolated, idempotent mock stores. Repeated executions against the same seed state produce identical deterministic outcomes.

STAGE 3

VERIFY

Read-after-write verification queries the mock store post-mutation to ensure requested fields match actual state without unintended side effects.

STAGE 4

RECOVER

If verification fails, ticket data is malformed, or model JSON is invalid, the engine fails closed, reverting mutations and escalating to human review.

The Three Canonical Scenarios

The three representative benchmark test cases required by the Challenge 07 brief, validating routine grounded resolution, missing identifier handling, and mandatory escalation.

📦 SYN-001: Routine Grounded Order Status

Customer Input: "Where is order ORD-1042?"

Supplied Evidence: Order record ORD-1042 (delayed to 2026-10-21) and store policy SHP-03 (Delayed Shipments estimate policy).

Expected Route: self_service (Action: answer)

Mock Ticket Action: Sets status to draft_ready, assigns route self_service, stages grounded draft reply, and records evidence citations in internal notes.

❓ SYN-002: Missing Lookup Information

Customer Input: "My package is late. Can you check it?"

Supplied Evidence: None (no order identifier or customer record in message).

Expected Route: customer_question (Action: ask_customer)

Mock Ticket Action: Sets status to awaiting_customer_info, assigns route customer_question, drafts clarification prompt, and avoids hallucinating order data.

⚠️ SYN-003: Delivery Dispute After Delivered Scan

Customer Input: "I never received order ORD-2098, even though tracking says delivered."

Supplied Evidence: Order ORD-2098 (delivered scan on 2026-10-16) and policy DLV-02 (delivery dispute investigation).

Expected Route: human_review (Action: escalate)

Mock Ticket Action: Deterministic guardrail forces status to pending_review, assigns route human_review, and flags ticket for carrier dispute investigation.

Safety Boundaries & Privacy Guarantees

        

          Engineered to satisfy enterprise guardrail requirements and prevent unauthorized operations.
        


        

          

            
🛡️ Allowlisted Mutations Only

            

              The mock ticket store explicitly rejects any write request to unauthorized fields. Only status, assigned_route, draft_reply, and internal_notes can be updated. Attempts to alter payment or credit card numbers are blocked.
            

          

          

            
👤 Strict Session Isolation

            

              Every visitor receives an isolated mock state (via browser sessionStorage in static mode, or per-session UUIDs with 2-hour TTL in Python). No visitor's actions or state resets can ever affect another user.
            

          

          

            
🛑 Zero Data Persistence & Bounded Input

            

              Custom visitor messages are strictly bounded to 1,000 characters. Input text is processed entirely in ephemeral memory and is never logged to disk, persistent databases, or external analytics services.
            

          

          

            
🚫 No Localhost Exposure

            

              This public demo makes zero requests to localhost:11434 or any local machine. Local model inference is preserved exclusively for secure local CLI or app execution.
